# Agent架构说明

## 架构总览

本系统采用**单Agent Pipeline架构**。所有功能模块串联在一个FastAPI进程中，模块间通过函数调用和Pydantic数据模型传递数据。

```
graph TD
    A[用户上传教材] --> B[文件解析模块]
    B --> C[知识提取模块 - LLM]
    C --> D[图谱构建模块]
    D --> E[跨教材整合模块 - Embedding+LLM]
    E --> F[RAG问答模块 - FAISS+LLM]
    F --> G[对话模块 - LLM]
    E --> H[整合报告]
    D --> I[前端可视化 - ECharts]
    E --> I
```

## 模块职责

| 模块 | 文件 | 职责 |
|------|------|------|
| 文件解析 | services/parser.py | PDF/MD/TXT格式解析，章节识别，结构化输出 |
| 知识提取 | services/extractor.py | 调用DeepSeek API，从章节提取知识点和关系（JSON） |
| 图谱构建 | services/graph_builder.py | 逐章提取，合并节点和边，存入内存图库 |
| 向量嵌入 | services/embedder.py | BGE-small-zh模型管理，文本向量化，相似度计算 |
| 跨教材整合 | services/integrator.py | Embedding语义对齐+LLM合并决策，30%压缩 |
| RAG服务 | services/rag_service.py | 文本分块、FAISS索引、向量检索、引用生成 |
| 对话管理 | services/dialogue.py | 整合决策解释、教师反馈检测、决策修改 |

## 设计决策论证

### 为什么选择单Agent而非多Agent？

1. **比赛时间约束**：5小时比赛时限，多Agent架构需要额外的通信协议、状态同步、错误隔离代码，开发和调试成本高
2. **评分标准**：赛题明确说明"一个论证充分的单Agent方案可以比一个没想清楚就硬拆的三Agent方案得分更高"
3. **模块边界清晰**：Pipeline各阶段（解析→提取→整合→RAG）有明确的输入/输出接口，职责划分清楚，后续可自然演进为多Agent
4. **调试便利**：单进程内的函数调用比跨进程通信更容易追踪数据流和排查问题

### 为什么Prompt设计采用单章节处理？

- 每章节独立调用LLM提取知识点，避免单次prompt上下文过长
- 单章失败不影响其他章节（try/except隔离）
- 限制每本教材最多处理3章（MAX_CHAPTERS=3），控制总API调用时间

### 为什么整合采用双重对齐（Embedding + LLM）？

- **Embedding粗筛**：快速计算语义相似度，O(n²)但n在可控范围
- **LLM精判**：仅对高相似度候选对调用LLM，在成本和准确性间取得平衡
- 阈值0.8较低，减少漏报；LLM二次判断过滤误报

## RAG Pipeline设计

```
教材内容 → 分块(600字+100重叠) → BGE向量嵌入 → FAISS索引
用户提问 → 向量化 → Top-5检索 → Prompt注入 → DeepSeek生成 → 带引用回答
```

**分块粒度选择**：600字/chunk + 100字重叠
- 医学概念通常在一段内完整表达
- 重叠窗口防止知识点在边界被截断
- 对比实验：200字失去上下文，1000字稀释检索精度

## 已知局限与改进方向

1. **内存存储**：当前教材和图谱数据存储在内存dict中，服务重启丢失。改进方向：引入SQLite或文件持久化
2. **章节限制**：图谱构建仅处理前3章，未覆盖教材全部内容。改进方向：异步任务队列+进度回调，支持全量处理
3. **图谱节点限制**：前端力导向图仅显示Top 50节点。改进方向：实现节点聚类、缩放时动态加载
4. **单线程LLM调用**：逐章串行调用DeepSeek API。改进方向：异步并发调用，大幅缩短构建时间
5. **决策修改**：对话中的决策修改基于关键词检测，较简单。改进方向：引入function calling让LLM自主调用决策修改API
